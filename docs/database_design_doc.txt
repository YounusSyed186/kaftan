Total: 19 planned tables, including the optional competition_prizes table. The agreed design does not include categories, subscribers, separate SEO tables, analytics tables, newsletter tables, user_roles, orders, inventory or checkout.
1. What this database is for
KAFTAN is planned as a fashion editorial publication first. The database should make it possible for the team to publish stories, manage photography for different screen sizes, arrange the landing page, show selected products, run a competition and manage sponsored placements from an admin panel.
One shared articles table for all editorial formats.
No required categories table. Navigation links and homepage sections are managed separately.
One products table only; this is not a full online store.
One active competition is expected at a time, while past competitions and entries can remain stored.
Desktop, tablet and mobile images can be selected independently for the same placement.
Each user has one role, assigned directly through users.role_id.
2. Editorial content

Important distinction: article_type says what kind of story it is; content_type says whether it is original, sponsored or affiliate. A fashion editorial can be either original or sponsored.
authors
Stores a contributor's name, unique profile slug, biography, optional profile image, website and social links. The profile image refers to media_assets.
article_authors
Connects an article to contributors. It stores article_id, author_id, contribution_type (writer, photographer, stylist, editor, etc.) and display_order. This allows more than one contributor per story.
Stores saved versions of an article, including the article reference, revision number, title, excerpt, body, person who saved the revision and timestamp. Revision numbers must be unique within each article.

Stores optimised copies created from an original image. Each record includes the original media_asset_id, its own storage key, variant name, width, height, format, file size and creation time. Example variants include a wide hero crop, a portrait mobile crop and smaller card sizes.

An image placement must belong to exactly one supported content owner. Enforce this with a database check constraint or use separate, strongly linked placement tables if stricter relationships are needed.
If no mobile image is supplied, the website should fall back to the desktop image or a suitable generated crop; it must not show a blank image.
The admin panel should preview the intended desktop and mobile layouts before publishing.
Use responsive image delivery in the website so the browser loads an appropriate image for the screen and layout.
Validate uploads and preserve image credit and licensing information.

homepage_items
Defines what appears inside each homepage section and in what order. Each item references exactly one article, product, campaign or ad creative. It can include a display position, optional title and excerpt overrides, visibility dates and an active flag.
Use database foreign keys for each supported content reference and a check constraint that requires exactly one reference to be filled in. Do not use a generic content ID with no enforced relationship.
navigation_items
Stores the label, URL, optional parent item, display position, active state and whether the link opens in a new tab. Parent-child relationships allow dropdowns. Navigation labels such as Style or Designers do not require an article categories table.

6. Competition
competitions
Stores the title, slug, description, prize summary, terms, start and end times, status, creator and timestamps. Suggested statuses are draft, scheduled, active, closed and completed.
competition_entries
Stores each participant's competition reference, name, email, optional phone, form answers, submission time, verification status and eligibility. Competition-specific answers can be stored in a structured field when the form differs between competitions.
competition_prizes (optional)
Only needed if a competition can have multiple prizes. Stores the competition reference, prize title, description, quantity and display order. If each competition always has one prize, keep prize information on competitions and omit this table.
The site should permit only one active competition at a time. Enforce that rule in the database or through a transaction-safe application rule. If a winning entry is stored on the competition, verify that it belongs to that same competition.
7. Sponsorship and advertising
sponsors
Stores a brand's name, unique slug, optional logo image, website, description, contact details and status.
campaigns
Stores a campaign's sponsor, name, description, start and end dates, status and timestamps.
sponsored_content
Links an article to a campaign and stores the disclosure text shown to readers. Avoid duplicate links for the same article and campaign.
ad_placements
Defines available advertising slots, with a name, unique key, description, supported layouts and active status.
ad_creatives
Stores a campaign's ad placement, headline, copy, destination URL, desktop and optional mobile image, active dates and status. The admin can preview device-specific creatives before activation.
Sponsored stories should be clearly disclosed. Campaign dates and status should be checked before showing a campaign or creative.
8. Users and roles
users
Stores the user's name, unique email, role_id, account status, last login and timestamps. role is stored directly on the user record. Each user has one role, as agreed; there is no user_roles join table.
If the application uses a managed identity provider, store its user identifier and do not manage passwords locally.
If local passwords are used, store only a secure password hash; never store plain-text passwords.
Enforce permissions on the server, not only by hiding buttons in the admin interface.
Use foreign keys from created_by, updated_by and uploaded_by fields to users where applicable.
9. Relationships and rules at a glance
An article can have multiple contributors through article_authors.
An article can have many revisions and image placements.
An original media asset can have multiple optimised variants.
A homepage section contains ordered homepage items.
Each homepage item points to exactly one supported content type: article, product, campaign or ad creative.
Each image placement points to exactly one supported owner and can have desktop, tablet and mobile image references.
A sponsor can have multiple campaigns; a campaign can support multiple sponsored articles and advertising creatives.
A competition can have many entries and, optionally, multiple prizes.
Each user references one role.
10. Data quality, security and performance
Use unique constraints for article slugs, product slugs, author slugs, sponsor slugs, role names and navigation/section keys where applicable.
Use foreign keys for relationships and choose deletion rules carefully. Preserve published content and historical records rather than cascading deletions indiscriminately.
Add indexes for published articles by publication date, homepage items by section and position, competition entries by competition and submission time, and campaign/ad schedules.
Use consistent created_at and updated_at timestamps. Update updated_at through a reliable application or database mechanism.
Validate date ranges, prices, statuses, URLs, image dimensions and uploaded file types.
Restrict admin access and permissions on the server. Keep secrets and credentials out of public client code.
Back up the database and object storage. Test restoring both, not just the database.
Use database migrations so schema changes are versioned and repeatable.
Do not store image binaries directly in PostgreSQL; store image files in object storage and their metadata and keys in the database.
11. Recommended implementation order
Create users, then media_assets and authors.
Create media_variants and content_images; implement responsive image upload, selection and preview in the admin panel.
Create homepage_sections, homepage_items and navigation_items.
Create products and competition tables.
Create sponsors, campaigns, sponsored_content, ad_placements and ad_creatives.
Add constraints, indexes, permissions, backups and seed data; test the complete editorial workflow before launch.
12. Explicitly out of scope
The agreed first version does not include mandatory categories, subscribers, a separate SEO module, analytics tables, newsletter tables, user_roles, a full e-commerce system, inventory, orders, checkout or payment processing. Basic SEO title and description fields may remain directly on articles without introducing separate SEO tables.
Final design principle
Keep articles as the main content record, keep all uploaded images in a shared media library, and let homepage placements reference content instead of duplicating it. This gives KAFTAN a manageable editorial system while allowing editors to control desktop and mobile imagery from the admin panel.
